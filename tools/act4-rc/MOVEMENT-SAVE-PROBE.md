# Stage 33 movement-save investigation

The stage 33/34 worker reported a real round-9 mid-turn rollback in `277cbbf1a2877042c479bfeaa9b6d3041ae1064d`, `game/reports/act4-rc-stage33-34/README.md`. The live export and reload differed; that evidence is not negated by this narrower check. The underlying cause remains unproven. In `shared/runtime/main.js`, the periodic battle snapshot is gated by `dirty`, and `pagehide` only cancels input; `Engine.move` itself emits no save event. Other game events can mark a battle dirty, so that observation alone does not prove why the recorded round-9 save was stale.

An isolated QA Chromium check used the RC preview source based on `43b268873` plus uncommitted subtitle sequencing changes. It declared stages 1–32 complete in the 45 SP fixture and entered stage 33 directly; it was not a normal playthrough. Two separate rightward keyboard movements and same-context reload/Continue were observed. After the second movement, both the live and stored archer were x=294.1936407618098, y=2242.5372386080403, moveLeft=2451.0701070040323; reload restored those values. Thus this initial-state probe did not reproduce the reported later-round defect. `browser-move-save-probe.py` repeats this limited observation on the QA URL in `HONRO_QA_URL` and prints values; it is not a passing regression test for the reported bug.

Next: preserve and obtain the original round-9 pre/post UI exports and localStorage raw snapshot, verify the exact build and save events, then reproduce the same active actor and mission state. Test ordinary walking, jump/landing, interruption, pagehide, quota failure and duplicate rewards before merging any fix. The separate stage 34 event clock rollback remains unresolved. No storage policy was changed on this evidence.

## Confirmed after-action regression and candidate fix

A second isolated UI probe first defended normally, waited for the next active mage and `dirty=false`, then walked without attacking or defending. Before the fix, live x=341.3806601870461 while the stored x remained 189, even after the autosave interval; a later jump produced a separate save signal. The historical round-9 original exports from `2a8242ac181019845d711fece75c1767c84dd8c9` have compressed SHA-256 `32885c72b4ad9497f221b6b2fc889f8d50d31f33190f4db688ab701d9cb1f16d`; they do not include pre/post localStorage, so they do not establish their own last write time.

The candidate marks actual active actor motion dirty in aim and preserves the existing 1.2-second batched save; pagehide and hiding flush pending battle state. Separate real Chromium probes observed (1) walking after an action, settled save and reload with matching x/y/movement, (2) jump/movement and landing with matching save/reload, and (3) immediate reload while dirty with live x=224.20274090108003 and stale stored x=201.83057747469104 before pagehide, restored at the live position afterwards. Scripts `browser-move-after-action.py` and `browser-move-pagehide.py` use declared entry fixtures and actual keyboard/reload. They do not constitute a fresh whole-stage clear or device performance test. Existing `act4-rc-archive` quota preservation passed. Broader existing stage 1–30 and custom/workshop regression and duplicate reward tests remain release gates.
