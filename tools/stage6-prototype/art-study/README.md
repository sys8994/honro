# Stage 6 rock material study (not integrated)

This is an isolated material study, not a stage BODY or a gameplay-ready asset. `rock-study.png` is a generated modular rock concept based on the dusk-green palette and material language of the earlier Stage 6 concept; its silhouette is not the game's collision and must not be scaled into place as a floor. The prototype's physical source is `tools/stage6-prototype/author.mjs`, SHA-256 `1c3f1f1825e39cabf653688ed779dcc42d80ce448e4e582173a8eb53cbb80870` at the time of this study. It remains unapproved geography.

`rock-study-raw.svg` is the Inkscape 1.4 trace, with the original reference preserved separately as PNG. Trace Bitmap settings: Multicolor / Colors, 8 scans, smooth and stack off, speckles 2, smooth corners 1.00, optimize 0.200. The near-white background trace and embedded reference were removed. It is a raw trace, not an optimized runtime asset. It has seven large color paths and substantial fine texture. An Inkscape Simplify 0.002 experiment produced holes and was rejected, not committed as a candidate. The render was reviewed at 1086×362 against the source; the broad rock bands remain, but high-frequency texture and unsupported slope prevent acceptance. No source-to-runtime JSON, collision alignment, bridge components, gameplay, mobile or final review is claimed.

Next: make separated source-traced rock/bridge components with controlled texture, fit to the actual stabilized physical contour without adding visible support surfaces, perform bounded optimization preserving contact edges, compile through `tools/vector-production/import-svg.py`, and review actual gameplay cameras and input play. The old BODY is locked to different geometry and must not be silently reprojected.

## Cleaner module experiment

`rock-module.png` is a separate generated solid-color rock concept. Inkscape 1.4 Trace Bitmap used Multicolor / Colors, eight scans, Stack on, smooth off, speckles 2, smooth corners 1.00 and optimize 0.200. The near-white background and embedded raster reference were removed from `rock-module-raw.svg`; the PNG is retained separately. It is an independent rock component, not a collision surface or a finished map. Raw SHA-256: `175ffe0fdb49bc57aa5300e153333a181cabcbe494a89f644a2d24f7f70aad3a`.

A non-cumulative Inkscape simplification search at 1086×362 and 2172×724 selected 0.0003. The raw trace contained 1181 commands; the candidate contains 756 and 31 subpaths, 39,337 SVG bytes. At 1× RGB MAE was 0.126/255 and maximum silhouette offset 1 px; at 2× RGB MAE was 0.103/255 and maximum silhouette offset 1 px. There were no contact-edge protections in this independent unplaced material study, so these numbers do not approve an eventual ground contact. The 0.001 candidate failed the silhouette limit. I inspected the raw/optimized comparison and standalone actual vector renderer; large facets and the outer form remain readable. `rock-module-runtime.json` is generated with the adjacent explicit config through `tools/vector-production/import-svg.py`; the normal vector/environment validators returned zero errors. The foot in that config is placeholder metadata, not a verified support anchor. Placement, source-to-contour fit, bridge work, runtime gameplay cameras, mobile, and final review remain open.

## Bridge-pier trace experiment (rejected)

`pier.png` is an isolated generated pier concept with a top socket, diagonal brace and stone footing. `pier-raw.svg` is an Inkscape 1.4 eight-color stacked trace, with raster and near-white background removed. At 512×768 and 1024×1536, a non-cumulative optimization search protected the top and footing regions. The 13,581-command raw trace failed the default runtime import because an inseparable path component exceeds 60,000 characters. The importer’s supported `preserveCompounds` mode preserves the fill operation and does import and validate the raw trace; a standalone 512×768 renderer check took approximately 85 ms for first draw and 0.4 ms warm on this machine, not a mobile performance result. Simplify 0.00001, 0.0001 and 0.0003 and four-digit precision did not satisfy both default import budget and protected-region quality. No optimized pier runtime JSON or map placement is offered. It also lacks stage-specific measured socket/ground positions. Generate or author a cleaner separable component before placement.

## Geometry-guided three-section preview

The west-matched, middle-guided and east-guided PNGs are three separately generated material concepts, each based on the corresponding `*-guide.png` generated from the exact prototype contour. They are not geometry sources. Inkscape 1.4 produced independent stacked eight-color traces, with the reference bitmap and white background removed. For each `*-grounded-raw.svg`, Inkscape intersections cut the traced paths to a region beginning 10 source pixels below the guide's ground line, removing guide-line/bridge artifacts; the preview BODY's exact road substrate supplies the contact edge. The 10-pixel value is a source-art cleanup margin, not a physics or road change.

The selected `*-optimized.svg` files are non-cumulative Inkscape Simplify 0.001 candidates. At 821×479 and 1642×958 their raw-to-candidate RGB mean errors are below 0.2/255 and silhouette offsets at most 1 pixel. The optimizer was corrected to count the importer's supported `dParts` chunks, and the west candidate then passed the existing import and pixel limits. This does not relax SVG/import limits. The three `*-runtime.json` files are compiled with their adjacent configs and were inspected as standalone renders. No important ground contact is inferred from these raster comparisons: the exact road path is a separate runtime clip and underpaint.

`art-preview.mjs` assembles these three sources in their guide coordinate rectangles and adds three nonphysical pier instances with deck/ground registration. It runs only when `HONRO_STAGE6_ART_PREVIEW=1`; this is a deliberately unshipped, review-only build, not an accepted stage. A standalone composition inspection revealed seams and repeated pier forms; an actual browser, close camera, mobile, support contact and gameplay review remain necessary. The pier uses the unoptimized raw trace, so runtime budgeting remains open. Geometry SHA-256 is locked by the preview author. The production build defaults are unchanged and the normal release gate is not replaced.

## Deeper BODY replacement under review

The first runtime overview exposed horizontal rectangular ends because the initial three source sections stopped within the camera view. `deep-west`, `deep-middle` and `deep-east2` are new independent concepts using geometry guides whose lower edge is world y=5500. Each trace was made in Inkscape 1.4 with eight stacked color scans, then intersected in Inkscape with the exact source-space lower-road contour plus a 10-source-pixel cleanup margin. This removes the temporary guide line while leaving the contact edge to the unchanged road substrate. Their editing source PNGs, guide PNGs, raw trace, grounded raw SVGs, optimized SVGs, configs and generated runtime JSON are retained. `deep-east` is the rejected trace with an unwanted bright blotch; `deep-east2` is the separately generated cleanup and is the one used.

The Inkscape 0.001 non-cumulative candidates pass the existing importer and 1×/2× comparison limits; measurements and SHA-256 values are in `deep-metrics.json`. Raw/optimized and standalone runtime renders were inspected, including the previously defective east area. The resulting section extents and their source-to-world transforms remain a preview. Actual camera/domain coverage, seams, the raw pier's performance and joinery, mobile visibility, and gameplay integration have not yet passed.
