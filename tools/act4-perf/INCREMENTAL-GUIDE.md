Source `e6f1cc19438f6f2ce9e3231c0449abec365b6d2a`; frozen RC world SHA-256 `99c59777254cb4942d5bfc7b7398068fc294dc29ff7208ac5f468953ecf5e581` and original 31–40 candidates, not the later 33/34 art. The isolated QA build also contains the independently developed compact autosave and `4ebe01b0bde5438782a7bd37e5dffdf89984f8ba` stage-40 dirty fix; 4ebe is not included in this branch. No Pages or production deployment.

`validate` now drains the same generator used for optional preparation. It retains the existing path, compound, token, clip, symbol and asset limits and errors, yielding between nodes/clip paths and at most every 256 compound numeric tokens (and during arc checks). A private snapshot is validated completely before paths are built. Each idle slice has a **soft** 3ms loop budget and checks the idle deadline, eligibility and abort signal; an individual regex, Path2D construction, JSON snapshot or final equality check cannot be preempted. An exact recursive own-data-property comparison to the live battle vector is required before the complete result is published. First actual draw rechecks the prepared snapshot and falls back to normal synchronous validation on any change. While pending, the renderer uses its normal validating synchronous path; it never consumes a partial result. A synchronous draw winning the race prevents replacement. Non-JSON data, cancellation, unsupported idle callbacks or errors simply leave the normal renderer responsible.

Only official, non-custom stage 40 is scheduled, only while its real App dialogue is open, visible and in the same battle. Eligible native-art battle landmarks whose bounds intersect the view expanded by two view widths/heights are prepared sequentially. The preparer stops on keyboard/pointer input, hidden/pagehide, dialogue close, stage change or landmark/vector replacement. Preflight skips vectors with source SVG, >2 million path/clip characters, >100,000 characters in one compound/clip, excessive node/symbol counts, or unusual shapes; these limits apply only to optional preparation and do not alter runtime validation. Snapshot memory is retained for successfully prewarmed vectors until first draw or collection; heap/GPU memory was not measured. The existing Path2D cache contract after an ordinary first draw is unchanged.

`tests/vector-incremental-prepare.mjs` compares the synchronous validator to the frozen original over restored stage-40 vector assets and valid/invalid fixtures; without restored candidates it runs the smaller committed fixtures only. It tests invalid input, cancellation, eligibility loss, mutation before publication (including an omitted JSON property), mutation after publication, synchronous-render races and no partial cache use. `tests/vector-assets.mjs`, `tests/vector-compound-parts.mjs`, `tests/vector-incremental-prepare.mjs` and `tests/act4-pilot-native-art.mjs` passed. They do not establish all possible authored/custom vectors or actual phone performance.

## Chromium comparison

Single active target Chromium instance, 5 allocated CPUs, PC 1440×900 DPR1, local uncompressed QA server, fresh contexts. Available RAM and host load are in raw records; other system activity is not controlled. Each run uses the same declared synthetic 45-SP profile and direct real `HonroApp.launch(40)`, waits six seconds in actual stage dialogue, then sends a real Enter key. The input-to-handler interval below includes Playwright/protocol scheduling, is one event per run and is **not** hardware input latency or a p95. Camera/time are set to the same water location only after dialogue; App loop is stopped for 20 fixed water draws. The initial synthetic entry is not normal title-button or full-play verification. First render measured from `ensureStage` includes loading and real App launch but excludes title navigation. rAF values are median/p95/max; p95 is nearest-rank. Two baseline and two final-candidate samples were interleaved with other scoped experiments, not measured on an exclusive host.
