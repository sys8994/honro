# Scale-keyed terrain tile reuse experiment — not adopted

The frozen RC world is `99c59777254cb4942d5bfc7b7398068fc294dc29ff7208ac5f468953ecf5e581`. The disposable QA renderer retained tiles from multiple raster scales under the same battle/session, sceneVersion, dimensions and appearance key, with the existing global 24-PC/12-mobile tile cap. Each tile still used its original scale, geometry, gutter, clip and paint sequence; no art, quality, pixel ratio or camera limit changed. This is an experiment, not a production change. An ordinary scale transition previously released the prior bucket, incidentally guaranteeing repaint on return. Before adoption, the complete invalidation contract across dynamic terrain, water, asset mutations and lifecycle/resize must be proven; the scale-key alone does not establish it.

`zoom-roundtrip.py` stops the App loop and uses a declared stage entry, PC 1440×900 DPR1, fixed scene and three 16-frame .94→.60→.94 camera sequences. A separate 12-frame water-location sequence changes `scene.time` while zooming .35→.45→.35. Timings are `Scene.render` CPU durations, with asynchronous full-canvas SHA-256 computed after each frame outside the timing interval; not normal input or phone FPS. Exactly one target browser was active. CPU/RAM/load were not sampled at the time, so these are not fully resource-controlled performance comparisons. Candidate/baseline and baseline/candidate order were both used across two sequences, on a shared host. Each 16-frame cycle has nearest-rank p95 equal to its maximum. Every one of the 108 fixed-sequence hashes per stage matched (48 frames in each of two sequences plus 12 water frames in the second sequence). Hash parity is scoped to these 108 frames per stage, not all clip/hole/opacity/transform states.

In the second sequence, 38 baseline/candidate builds were 48/36 on cycle 0 and 48/24 on cycles 1–2; respective p95/max were 129.2/109.9, 120.6/148.6 and 114.8/130.7ms. For 40 the build counts were 44/30 then 44/20; p95/max 125.1/138.2, 178.9/99.6 and 132.5/103.0ms. Water-location first/maximum draw remained 191.9/208.7ms on 38 and 496.0/497.1ms on 40. Median values and all frames/counters are in the archive. The fewer rebuilds and some warm zoom improvements are real within this fixture, but 38's p95 worsened in the repeat and cold water remains unresolved. No overall performance pass is claimed.

The experimental patch, full timings, counters and per-frame hashes are in `evidence/multiscale-experiment.tar.xz`, SHA-256 `e55fd6372dc80707e7d4ec39c4d76a050222e003703877447aadeed0065197f9`. It was reverted from the QA build and never committed to runtime. Future work needs invalidation tests with actual state changes and mobile DPR, resource-accounted repeated normal inputs, cold water and visual regression before any reconsideration. Rejected screen-raster settling and group-clip experiments remain rejected.

## Cold water Path2D diagnostic

A separate fixed-camera stage-40 run instrumented `Path2D` construction stack traces, then repeated with vector draw timing; instrumentation changes cost and results are not comparable as a performance benchmark. On first water-location entry, 233 Path2D constructions were observed; stack samples originate in `HonroVectorArt.prepare` while drawing landmarks. In one instrumented run the longest individual draw was `approved40:terrain-right-join` at 70.7ms; first draws of several stair/wood/pile/ramp assets were about 15–25ms. These are nested, instrumented call durations and must not be summed or generalized. They identify vector preparation as a candidate contributor, not the entire 622ms render. Splitting/preparing paths asynchronously could move work or change paint/clip semantics; no such fix has been verified or adopted. No CPU/RAM/process census was captured at this diagnostic point. Reproduction: `water-path-stacks.py --base http://127.0.0.1:8770 --tag water-assets --stage 40`; raw stacks and timings `evidence/water-path-stacks.tar.xz`, SHA-256 `e2e169175007530740edf71d46e1945a48afa8d017bf1aee189029448b984607`.
