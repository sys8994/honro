# Official art trust boundary and asynchronous snapshot design

**Conclusion: no runtime optimization is proposed.** Source audited and measured is current common `0dd7a9a92a77b1e06d80f8e2fd24e09e40fccceb` (integrated exact-content signature cache `b5995759`, byte-identical to `6963180f`); QA uses original frozen 31–40 world SHA-256 `99c59777254cb4942d5bfc7b7398068fc294dc29ff7208ac5f468953ecf5e581`. Common changes since `23e8204a` in this range are `profile-store.js` plus test/documentation; the isolated 23e QA had that exact integrated file copied and rebuilt. Revised 33/34 art and actual phones are not covered. No runtime source was modified in this branch, no deployment.

## Loader, ownership, and mutation audit

- `shared/web-loader.js` `request`/`workerParse` decode JSON in a worker (or main-thread fallback); worker messages structured-clone parsed results and `loadData` then unpacks and hydrates asset URLs. The request cache is shared and `loadData` is exported. `ensureStage` assembles the library, runs ordered authors, then registers the original library objects in `project.library`, publicly reachable as `HONRO_PROJECT`. A trustworthy post-parse boundary would have to account for hydration, author passes, split-resource provenance, identical IDs in later stages and mutable public replacement. A plain prototype or `Object.isFrozen` on only the root is not such a boundary; parsing something originally as JSON does not prove its current descendants or current reference have not been replaced since publication.
- `shared/map/schema.js` `normalize` makes a full JSON clone before filling defaults; `shared/map/compiler.js` `compile` JSON-clones each source asset for the battle. For a fresh element its landmark and element initially share that cloned asset; it is **not** the provider. `profile-store.js` `restoreBattleArt` validates all refs first, then `structuredClone`s each replacement individually, producing separate mutable live copies. `act4-events.js` snapshot and portable export also create JSON copies. Existing copies deliberately preserve the ability to hold user changes inline rather than requiring mutation of the provider.
- `identity-boundary-probe.py` used actual title UI import and Continue of the real 40 boarding checkpoint, then user-facing pause → retry → restart. In **both** the restored round-16 and fresh round-1 battles, 26 asset placements had the same JSON value as the corresponding provider but **0/26 asset identities and 0/26 vector identities matched the provider**. None of those live/provider root objects was frozen, and all 26 live `vector` properties were writable. Freshly compiled pairs had 13 shared duplicate live assets; restored copies had zero. This is one chapter/checkpoint and a UI retry, not a proof of every stage or a natural full playthrough.
- Existing editing paths often copy first: `workshop/src/app.js` `newProject()` deep-copies `HONRO_PROJECT`, `HonroMaps.commands.apply` clones its input, and terrain-derived visual edits in `shared/map/terrain-domain.js` clone the asset before modifying it. But this is not a general live battle copy-on-write contract: `shared/map/open-structures.js` has a direct battle asset `oneWay` mutation on matching older-stage migration rows (the current rows contain none for 31–40), while the workshop exposes direct edits to its independent project. Engine terrain damage/changes mutate battle terrain and `sceneVersion`. Stage 40 did not demonstrate an official-art mutation in this limited search, but freezing its publicly reachable provider or replacing live mutable art with shared frozen refs would change existing mutation behavior, and no exhaustive, enforced COW boundary or post-registration substitution guard was found. Do not infer that every official artifact is deeply immutable merely because current art matches.

A viable future trusted-loader design would need a private registration of values produced by the actual parser **after all required hydration/author mutations**, explicit official ID/version/content provenance, recursively immutable own data throughout the registered graph before external exposure, and a tested editing API that makes a mutable copy before any change. Battle attachment/reload would need to preserve that registered immutable value *or* atomically verify a separate mutable clone; today neither happens. Unknown/custom/modified data, unsupported objects or any reference replacement must use current exact serialization, and legacy 33 signatures and raw exports must remain valid. The rejected Proxy structural-comparison experiment cannot establish such provenance. No deep-freeze/shared-reference implementation is safe to adopt on the present evidence.

## Why naive asynchronous copying is not atomic

`App.flushBattleSave` currently clears a boolean `dirty`, synchronizes roster, and invokes synchronous persistence; moving units and 40's escort clock set the same boolean, and multiple writes can occur while it is already true. Story reader/receipt updates, outcomes, import/restore, progress/equipment, terrain mutations, and provider changes have additional paths. `sceneVersion` is a rendering/terrain invalidator, not a complete battle/profile/provider mutation generation. Reading half a live graph, yielding, and reading the rest can combine an old boat position with a new passenger position while `dirty` is true both times. `async-snapshot-atomicity-probe.mjs` demonstrates exactly that synthetic counterexample; it is not production save code.

A plausible *future* design must first provide and test one of: (a) a single atomic point-in-time snapshot with measured bounded synchronous capture; or (b) an enforced persistent/COW battle, profile, reader and provider graph with complete monotonic mutation generations covering every writer. An async preparation attempt would capture a generation and battle/session/profile identity; be cancelled or rejected if any covered state changes; publish only a complete, validated result; and mark clean only the exact committed generation. A single writer with monotonic commit IDs must prevent an older worker result from overwriting newer story, outcome, import, reload or profile data. Under continuous movement, retries need a bounded fallback that actually saves rather than starving. Custom/edited/unsupported assets and unavailable worker must keep a correct path. `pagehide` and hidden-tab handling already invoke synchronous flush; an async-only worker completion cannot be assumed before suspension or process termination. Synchronous callers and save-failure/recovery UI must keep their return/failure semantics, atomic `localStorage.setItem`, archived old bytes, reader/receipt consistency, export portability and import sequencing. These requirements are a design gate, not an implemented solution.

## Actual Worker transfer measurement

On common `0dd7a9a9`, the same real checkpoint was UI imported and continued, then **App.frame was stopped** to keep the battle fixed. An experimental Worker received the entire live battle via `postMessage`, serialized it and computed SHA-256, and returned its hash/length; it did **not** perform a save or access `localStorage`. Each of five replies per run matched that run's original 30,780,251-character battle JSON hash and the live battle remained unchanged. This shows structured-clone fidelity for this fixed fixture only. Worker completion includes JSON serialization, SHA computation and communication; it is not a measurement of a real storage pipeline.

Single Chromium 154 headless PC, 1440×900 DPR1, SwiftShader/software Canvas, 5 allocated CPUs, 10 live Chromium processes, ~14.5 GiB available RAM. Each run did three `structuredClone` calls and five Worker messages; order reversed between runs. The worker was created once per run, with one request in flight:

| Order | Synchronous `structuredClone` ms (3) | main-thread `postMessage` return ms (5) | worker response elapsed ms (5) | sampled rAF median / p95 / max ms during Worker loop |
|---|---|---|---|---|
| clone first | 64.4, 118.8, 70.4 | 62.1, 21.5, 22.0, 22.9, 158.3 | 294.0–694.2 | 16.7 / 16.8 / 150.0 (152 frames) |
| worker first | 49.6, 32.6, 37.8 | 22.2, 22.3, 39.6, 60.6, 22.8 | 329.1–485.1 | 16.7 / 16.8 / 49.9 (120 frames) |

Calls and frame intervals overlap; do not sum them. Full raw `postMessage` has substantial synchronous structured-clone cost and variable outliers; the results do not establish a safe replacement for the existing ~44ms warm compact autosave. Worker completion includes the deliberately added hash; no causal explanation for the 158ms outlier is established. Stopped gameplay and PC headless instrumentation do not measure real movement, input latency or phone performance. Transferable buffers would require producing a coherent transferable representation first; serializing the full live graph on the main thread merely moves the blocking point. An independently validated structured static/mutable split might reduce it, but the current runtime does not yet prove that split immutable and atomic.
