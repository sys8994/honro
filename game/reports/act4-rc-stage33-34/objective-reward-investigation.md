# Stage 33 objective reward investigation

The all-upper clear's zero XP was not a replay or duplicate-payment rejection. Both the 7-turn lower and 8-turn all-upper runs started with no stage 33 clear, no stage 33 objective evidence, and an uncompleted contribution ledger with nothing paid, spent, or forfeited. All four heroes started at 158091 XP. The entry profiles are preserved locally under `/workspace/honro-snapshots/current33-lower/entry-1793476377174-3d62bcd9aede.json` (SHA-256 `3d62bcd9aedec7aab4303b4f3284ce643bd9b45718f7e069c5efccd8f08f3a60`) and `/workspace/honro-snapshots/current33-upper-probe/entry-1793479490275-7e4562d1be24.json` (`7e4562d1be2415653e3ea3a2c82d71b7bb3e7fb47cc9f8e0061c3e90ab3b677f`). The fixture's previous 31–32 clears were synthetic, as described in README; these two actual stage 33 completions were not.

The lower run awarded archer 3109, mage 3669, knight 3346, occultist 3148 XP; the upper awarded zero. Both killed zero enemies. On completion their ledgers contained no objective entries. The lower's existing contribution calculation credited player support associated with environmental enemy progress; the upper's calculated reward weights contained only `_system`. In the upper result the existing 96412-XP stage budget was entirely forfeited. Thus 0 kills is not itself the switch and 0 XP is not proof of no threat. The actual attack and route evidence is in `route-pressure.md`.

## Contract and code

Inspection used source `40966b3184d4452727a46afabfe62c5da5dc33ff`. The actual runs used frozen source `aba9f38b39276ad8238d67986a5f83192751edb1`; their observed outcomes are not claimed as a new run on 40966.

`game/docs/OBJECTIVE_CONTRIBUTION_XP.md` describes finite evidence for actual arrival and mandatory party reunion, assigned to the actors responsible; its expressly documented coverage is chapters 1–30. It provides no explicit fixed stage-33 XP award. `game/docs/CONTRIBUTION_XP.md` specifies a finite existing stage budget, contribution-based allocation, system forfeiture, once-only ledger, and no repeat payout. The standard arrival helper's 20 is a contribution score, **not 20 XP or a fixed completion bonus**. The v3 and v4 contribution policies differ and v3 must be preserved.

`shared/data/act4/content.json` labels 33, 34, 37, 38 and 39 `objective: act4`. Stage 33's authored goal is reaching the high rocks beyond the tidal path; it does not prescribe enemy extermination or a numeric XP reward. In `shared/runtime/act4-coast-events.js`, 33/34/37/38 complete via their grounded, living-party exit condition (37 also requires its signal); 39 instead requires its stable exit and four safely rescued people. The optional 38 connection and other optional narrative are not automatically mandatory. No Act 4 objective-contribution calls were found in the Act 4 runtime modules. `objective-contributions.js`'s generic `beforeComplete` handles `arrival` and `rescue`, not `act4`, so these specific completion branches do not by themselves record that evidence. This is a source-level gap across these branches, not an assertion that every actual run in these chapters paid zero: combat and support evidence can still pay XP. Applying the 1–30 documented arrival principle to Act 4 is a supported design inference, not discovery of an explicitly authored Act 4 reward amount.

## Proposed narrow change and differential checks

For stage 33 only, after the existing actual, non-probe exit predicate succeeds and before completion, pass its living required party to the existing once-only arrival helper, with the actual exit bounds and a stable stage-specific token. Use the existing 20-point arrival convention and existing ledger allocation; do not change exit predicates, enemy requirements, overall stage budget, or already-cleared profiles. The existing version-4 evidence gate and completed/token checks must continue to apply; preserve v3 behavior. Whether analogous 34/37/38 exits and especially 39's distinct rescue actions should receive evidence requires their own causal attribution and verification, rather than granting a speculative common bonus.

Prepared checks: compare unchanged and candidate code on identical fresh normal stage 33 pre-interaction states for both routes; verify non-probe valid completion records only the actual required living actors, stays within the existing budget, and distributes XP through the existing ledger. Check invalid/incomplete exit, interaction probe, repeated interaction, same-context save/reload, and replay of an already-cleared or paid ledger do not mint new score or XP. Check version 3, custom battles, unrelated stages and defeat paths remain unchanged. Include the engine's causal assisted-arrival receipt case and caps. Follow with a normal UI clear/save/reload rather than treating unit checks as gameplay evidence.

As a preliminary accounting-only counterfactual, the production `contribution-xp.js` was run on a clone of the actual all-upper round-8 pre-E ledger (snapshot SHA-256 `6ba25173b16fd14831171e3be5c556e0ed54e4a819da0f51b200ea8827587ec8`). Supplying four equal credits under one synthetic arrival token added 5 score to each, rejected the duplicate token, and rejected another token after completion. With no XP caps supplied to this isolated calculation, the existing reserve function distributed 4819 total XP (1205, 1205, 1205, 1204) and forfeited 91593 of the original 96412 budget. The actual pre-E score included `_system: 380.13224418643983`. This is **not** a played or implemented fix, not a promised reward, and does not test the live exit predicate, growth caps, causal receipts, reload, or replay. Original snapshots were not modified. No runtime code was changed by this investigation.
