# 40장 연속 일반 입력 비교: 중간 근거

## 범위
공개 기준선 배치와 후보 배치를 같은 공식 runtime에서 비교했다. 원래 스폰과 42체를 유지하고 권장 진입 25레벨의 동일한 합성 훈련 프로필을 사용했다. 사용자 저장은 열거나 수정하지 않았다. 이후 move/jump/drop/fire/wait/select와 실제 턴 진행만 사용했다. coast와 pilot 공식 래퍼 및 실제 Canvas 예고를 적용했다.

이것은 app:false Engine 입력 검사이며 정상 App의 대화·주민·배 호송 완료 검사가 아니다. 적 삭제, HP·이동량 보충, 순간이동, 턴 강제 지정, 호송 상태 강제 완성은 하지 않았다. 결과는 특정 입력 정책과 프로필의 관측이며 보편적 난이도 판정이 아니다.

### 실제 예고 관측 및 행동 기록

실제 `HonroScene` 객체를 `HonroApp.scene`에 연결하고30tick마다 Canvas를 그렸다. `seen/offered/response`는 직접 대입하지 않았다. 다음은 후보의 최종 `honroPilotCombat.history` 기록이다.

|개체|warning|fired|bound|relocate|guard|
|---|---:|---:|---:|---:|---:|
|결박귀 final40-west-anchor-2|2|2|5|2|1|
|포격귀 final40-dock-right-3|1|1|0|1|0|
|수문장 final40-tide-keeper-1|2|2|0|2|2|

fired의 target에는 실제 `seen:true`, `offered`, `response`가 기록되었다. 이것은 실제 관측 후 행동이 진행됐다는 근거이며 모든 발사의 명중·피해를 입증하지 않는다. 특히 포격귀의 별도 국소 검사에서 지형 조기 충돌이 확인되어 후속 재배치 검증이 필요하다.

### 종료 판정의 엄격한 한계

후보 결과의 `phase:won`은 기본 Engine의 적 전멸 종료다. 실제 App은 `mount`에서 `e.checkEnd = () => this.checkMission(e)`로 목표 판정을 연결한다. 본 검사에는 그 App 대화/목표/주민 이동 루프가 없으므로 정상 게임 승리 또는 `quiet = !foes && stable && P.quietReady` 충족과 호송 완료로 바꿔 부르면 안 된다.

실제 App의 이벤트·대화 루프와 미완료 목표 판정을 연결한 후속 검사가 필요하다. 모든 적 처치, 최종 승선 복귀, 주민 승선/항해/상륙, 집결 및 종료 입력을 각각 확인해야 한다.
