# 전 막 지형 외곽·접합 검수 SOP

2026-11-20 적용 우선: 기존 1~5막의 감사 범위·최소 5회 반복 및 매회 전항목 검수 게이트는 [현행 지형 제작·최적화·검수 SOP](TERRAIN_PRODUCTION_REVIEW_SOP_20261120.md)로 보강한다. 좌우에 추가해 상단·하단과 네 모서리를 실제 허용 카메라에서 보고, 정상 AA와 형상으로 구워진 윤곽 띠를 구분한다. 이 문서의 결함분류와 최소수정 원칙은 계속 적용한다.

우선순위 변경(2026-11-20): 상하좌우와 네 모서리의 실제 더미 지형 연속성을 먼저 검수·수정하고, 통과한 실면적을 다시 계측한 뒤 노드를 최적화한다. 그 전의 감량 후보는 진단 자료로만 보존한다.

작성: 2026-11-17. 적용: 1~5막, 내부 stage 1~50. 확인한 master: `2614e4f4010f6785cedeb9d32f76010190c2d4b4`.

사용자 최신 지시인 “외곽, 접합 관련, 모든 막에서 전수조사”의 실행 기준이다. 먼저 이 항목에 집중하며 전투 난도·턴 수 등 게임플레이 정량 검수와 구별한다. **이 문서는 기준 수립이지 50장 검수 완료 보고가 아니다.** 전수의 단위는 모든 장의 외곽 구간·접합부·관련 상태이며, 연속적인 모든 카메라 좌표나 모든 기기의 모든 픽셀을 검사했다는 뜻이 아니다.

## 1. 기존 지침과 판정의 의미

- [새 버전 SOP](HONRO_NEW_VERSION_SOP.md), [지형 제작](TERRAIN_GENERATION_SOP.md), [벡터 저작](VECTOR_AUTHORING_SOP.md), [단일 지형 영역](TERRAIN_DOMAIN.md), [카메라 범위](CAMERA_BOUNDS.md)를 함께 적용한다. 공통 엔진·단일 지형 원본과 기존 충돌/진행/저장 계약을 유지한다.
- [취향서](taste/HONRO_TASTE_BIBLE.md)와 [취향 검수](taste/AI_TASTE_REVIEW.md)의 사용자 최종 판단을 대신하지 않는다. 아래 “통과”는 명시된 기술·연속성 조건의 확인이며 미감에 대한 사용자 승인이나 장 전체 제작 완료를 의미하지 않는다.
- [11월 15일 경로 점검](TERRAIN_PATH_AUDIT_20261115.md)의 50장 로드/카메라 표본과 최적화 비교는 재사용 가능한 근거다. 전 장 최신 외곽·접합 미술 검수의 완료 증명으로 전용하지 않는다.
- [1장 최근 공개 검사](ACT1_STAGE1_TERRAIN_REVIEW_20261117.md)도 데스크톱 표본이다. 모바일·파괴 후·모든 접점의 빈칸을 자동 통과시키지 않는다.
- 단계별 증거를 재사용하고 수정 영향 구간만 재검증한다. 이번 사용자가 명시한 전 장 외곽·접합 조사 외의 무관한 전체 검사를 추가하지 않는다.

## 2. 장별 조사 목록을 먼저 만든다

각 장 시작 시 최신 master와 현재 공개 배포를 각각 식별한다. 막/장/내부 ID, 저작·활성 공급 자산, BODY/REAR/SURFACE/근경, transform, clip/alpha, 실제 path 범위와 metadata bounds, Play/Camera/Visual/Terrain 영역을 읽는다.

장별 위치 번호를 부여해 다음을 빠짐없이 목록화한다.
1. 서·동·하부 외곽과 모서리, 위쪽 수관·가지·천장·탑 등 상부 실루엣.
2. 원본↔확장, 자산↔자산, 색면/clip/타일/캐시 경계, 지층·재질 전환, 구조물 기초·뿌리·교각.
3. 통로·동굴·아치·창 등 의도된 빈 영역, 좁은 발판·계단·one-way와 지지면.
4. 의도된 부유체와 낭떠러지, 물/수위·파괴·가림·퀘스트로 상태가 바뀌는 접합.

전체뷰에 번호를 표시하거나 월드 구간/자산 ID로 대응시킨다. 큰 가장자리의 양 끝만 보고 중간을 검사했다고 쓰지 않는다. 겹치는 카메라 이동 구간 또는 연속 캡처로 목록 전체를 덮고, 각 결함/민감 접점의 확대 증거를 남긴다.

**부유지형 분류:** 특히 5막 하늘우물의 의도된 부유 바위는 밑이 비었다는 이유로 채우지 않는다. 장 설계·원본 실루엣·지지 관계로 의도성을 확인한다. 바위가 자연스럽게 끝나는 형태와, 사각 source/clip/bounds에서 암면·나무·지지 구조가 동시에 잘리는 사고를 구별한다. 근거가 없으면 “의도 불명”으로 남기고 설정을 임의로 바꾸지 않는다.

## 3. 확인할 화면과 상태

아래 행렬을 **각 장에 적용**한다. 실제 수치를 기록하며 다른 장의 줌/범위를 복사하지 않는다.

| 관점 | 필수 확인 |
|---|---|
| 전체 구조 | 실제 Game 최소 줌의 전경, 각 외곽과 모든 접합 위치 목록의 연결 |
| 보행 가독성 | 실제 진입/보행 배율과 배우 크기, 각 접합·지지선·통로의 확대 |
| 카메라 | 현행 코드가 허용하는 좌/우/상/하 극단 pan 및 모서리, 줌 전환 중 타일 출현/소멸, 필요한 최대 확대 |
| 모바일 | 장별 세로 viewport, 필요한 가로/resize, 동일 위치의 핀치/팬 및 UI 가림; 길쭉한 viewport가 추가 외곽을 노출하면 포함 |
| 상태 변화 | 기본 상태와 해당 접합에 영향을 주는 파괴/수위/기믹/가림 전후, 캐시 재생성/재진입 |

- CSS viewport 너비×높이, DPR, renderer/브라우저, 카메라 x/y/zoom 또는 재현 가능한 UI 경로를 남긴다. 화면 캡처 해상도와 CSS 크기를 혼동하지 않는다.
- 모바일 viewport 에뮬레이션, Native Scene, 실제 모바일 기기를 구별한다. Native는 사전 진단/회귀용이며 공개 Game 실제 화면과 입력 검증을 대체하지 않는다.
- 기본과 보행 배율에서 목록의 접합을 읽고, 최대 확대는 결함/얇은 경계/접촉부 진단에 사용한다. 모든 배율의 무한 조합을 체크박스로 가장하지 않는다.
- 가능한 상태를 확인하지 못하면 미검수다. 해당 지형이 파괴 불가 등 소스 근거가 있을 때만 “해당 없음”으로 기록한다. 상태를 만들기 위한 강제 주입 결과는 정상 Game 입력 결과와 구별한다.
- 디버그 충돌 표시선과 실제 그림선을 분리해서 본다. 진단 오버레이를 끈 화면도 남긴다.

## 4. 기술적 통과 조건과 차단 기준

| 항목 | 확인 조건 |
|---|---|
| 외곽 연속 | 카메라로 노출되는 구간에서 지형/수관이 의도치 않게 직사각 절단되거나 배경이 비치는 틈이 없다. 자연스러운 절벽/부유체 실루엣은 보존된다. |
| 접합 | 기본/보행/축소에서 덧댄 사각 패치, 경계 밝은 띠, 중복 윤곽, 색층 단절·출렁임·타일 소멸이 드러나지 않는다. 색/암맥 방향/재질 규모는 기존 장소와 연결된다. |
| 공간과 가독성 | 2D 측면의 지지 관계를 유지한다. 가짜 밝은 상면/보행선, 거대한 늘인 단색 벽·반복 무늬·흐린 덮개로 문제를 숨기지 않는다. 배우와 실제 보행면이 읽힌다. |
| 보호 영역 | 원본 통로·아치·터널·건물·발판·가지와 기존 접촉선이 유지된다. 빈 공간을 무조건 사각형으로 파거나 암반으로 채우지 않는다. |
| 기능 보존 | 충돌/one-way/배우·목표·진행·저장에 의도하지 않은 변경이 없다. 그림의 발 위치와 실제 지지가 맞는다. |
| 재현 | 수정 전후 같은 구도/상태, 원인, 근거, 관련 검사와 최종 공개판이 연결된다. |

확정된 절단/틈·가짜 발판·통로 침범·의도된 부유체 훼손·데이터 회귀는 해당 장의 이 항목 완료를 차단한다. 취향 불확실성은 기존 승인 사례와 비교해 별도로 보고한다. 미세 장식 개선이나 서로 다른 rasterizer의 경계 AA 차이만으로 무관한 작업을 차단하지 않는다. 그러나 **실제 Game에서 보이는 접합선은 “1px 이하”라는 이유로 자동 허용하지 않는다.**

전체 평균 색 오차나 검사항목 개수, 임의 점수로 합격시키지 않는다. “화면에서 결함 관측 없음”은 관측 범위와 함께 쓰며 무결함의 절대 보증으로 확대하지 않는다.

## 5. 원인 분류 후 최소 수정

1. **누락/잘린 원본:** 실제 source alpha/path가 끝나는가? 시안의 캔버스 범위부터 확인한다.
2. **등록/범위 오류:** path는 이어지는데 viewBox·world transform·metadata bounds·culling/cache 범위가 잘못됐는가? 카메라를 옮겼을 때만 사라지는지 대조한다.
3. **합성 오류:** 반복 clip/alpha의 AA 누적, 배타 coverage 사이 틈, 정수 타일 경계, 잘못된 fill rule/구멍, 원본 밑색의 덮임인가?
4. **실제 미술 연결 실패:** 원본과 확장의 암면 규모·방향·색이 다르거나 단순 늘이기/패치 형태인가?

bounds/등록/합성만 잘못됐다면 소스 미술을 보존하고 원인만 고친다. 이 경우 불필요한 새 이미지 생성·Inkscape 재추적을 요구하지 않는다. 새 형상/질감이 필요한 경우에만 아래 제작 절차를 수행한다. 카메라 축소 제한, 배우 크기 변경, 충돌 dummy, 덮개 사각형으로 결함을 숨기지 않는다.

최근 사례:
- [41장 접합](STAGE41_JOIN_STATUS.md): 반복 clip의 coverage를 한 번 적용하고 배타 접합 coverage를 검증했다. 원본 구조선까지 없애는 작업과 구별한다.
- [48장 연속 지지](STAGE48_CONTINUITY_STATUS.md): 수평 어깨/재질 규모/사각 패치 때문에 후보를 반려했다. 기하 검사 통과만으로 연결 미술을 채택하지 않았다. 단일 coverage, 원본 보호와 터널 내부를 따로 검사했다.
- 지형 생성 SOP의 2장 정밀도와 3·5·9·10장 재질 크기 사례: 수치 통과/경량화 성공은 실제 배우 배율의 품질을 보장하지 않았다.

## 6. 새 미술이 필요한 수정의 제작 절차

스켈레톤·보호 영역·실제 카메라 노출 범위 → 시안 → 실제 배우 배율 사전 합성 → 실제 Inkscape 추적/편집 → 원본 보존 최적화 → 공통 엔진 연결 → 같은 위치 재검수.

- 기존 팔레트·암면 크기·방향·밝기 구조와 원경 분리를 지킨다. 원본을 단순 확대해 이어 붙이거나 임의 코드 폴리곤을 미술 시안 대신 만들지 않는다.
- native 합성은 일찍 사용해 큰 재질/공간 오류부터 발견한다. 실패한 시안을 정밀 최적화로 구제하려고 반복하지 않는다.
- raw/후보/최종, 이미지와 trace 입력 hash, Inkscape/도구 버전·옵션·transform·mask를 남긴다. 시안→raw 추적 오차와 raw→최적화 오차를 분리한다.
- 기존 벡터 SOP의 두 후보 우선 원칙과 현행 엔진 한도를 유지한다. 적합한 최적화 후보가 없으면 품질/예산을 만족하는 raw 채택 사유를 남긴다. 검사기를 완화해 통과시키지 않는다.
- path/segment/subpath/편집기 노드/실제 mesh face/원본 바이트/전송 바이트를 구별한다. 측정하지 않은 노드·면·FPS를 대리 지표로 주장하지 않는다. raw 대비 감량과 기존 출시판 대비 증감을 별도로 적는다. 새 지지체 추가를 기존보다 무조건 경량화했다고 쓰지 않는다.

## 7. 수치 측정과 보존 검사

- 오차: 같은 렌더러·배율·합성에서 전체 및 채색 영역, alpha 윤곽, 중요 ROI/구멍/얇은 지지선을 비교한다. 평균뿐 아니라 최대·국소 변화와 실패 위치를 기록한다.
- 임계값: 자산에 이미 적용되는 보호 오차/엔진 한도를 출처와 함께 사용한다. source px/world unit/screen CSS px를 구별하고 transform·zoom으로 화면 영향을 확인한다. 특정 장의 epsilon 또는 감량률을 전 장 공통 합격선으로 복사하지 않는다. 새 기준이 필요하면 보호해야 할 화면 기능과 측정 조건을 먼저 정하고 근거를 기록한다.
- 충돌·게임 데이터: 같은 파이프라인 단계의 원본/후보를 비교한다. 저작 데이터와 hook 이후 런타임 데이터를 섞어 가짜 실패를 만들지 않는다. 자산 변경 allowlist 외 데이터 동일성과 보호 접점/구멍 검사를 필요한 범위에서 수행한다.
- 저장: 자산 ID/서명/cache/스키마를 바꾸면 기존 전투 복원 영향도 검사한다. 미술 때문에 모든 장 revision을 올리지 않는다. 일반 사용자 저장을 덮지 않도록 분리된 검수 기록을 사용한다.
- 실제 조작: 바뀐 접지/통로를 정상 UI 이동·점프·착지로 짧게 확인하고 HP/이동도/조작 복귀를 기록한다. 단순 외곽 색 수정처럼 이동에 영향이 없으면 그 이유를 남겨 과잉 완주를 피한다.
- 성능: 변경이 부하/캐시를 늘리거나 실제 문제가 있으면 동일 조건 로딩/팬·줌/프레임 p50·p95·최대/메모리를 비교한다. 표본 환경을 적고 미측정 FPS 개선은 주장하지 않는다.
- 충돌 JSON 동일은 화면 접촉선 동일의 증거가 아니며, 짧은 착지 성공은 전 장 완주·전투 밸런스 통과가 아니다.

## 8. 순차 진행, 배포와 완료

장 하나의 목록 작성 → 조사 → 결함 분류 → 최소 수정 → 관련 검증 → 원격 보존 → 공개 확인 → 장 기록 정리 후 다음 장으로 진행한다. 막 경계나 5막만을 이유로 조사 대상을 생략하지 않는다. 의존 차단이 있으면 남은 항목과 이유를 명시하고 독립적으로 가능한 조사만 계속한다.

- 문서/코드/에셋의 일관된 변경 단위마다 커밋·원격 반영한다. 통합 직전 최신 master와 다른 작업을 재확인하고 강제 덮어쓰지 않는다.
- 런타임 변경은 공식 빌드/관련 CI, master, 기존 Pages의 해당 SHA/산출물 확인을 거친다. 로컬 공개 검증이 막혔다면 미검증 후보임을 밝히고 허용된 공식 경로만 사용한다. 실제 공개판에서 즉시 확인하기 전 완료로 표시하지 않는다.
- 공개판의 정상 진입·해당 접합 팬/줌·관련 입력을 직접 확인한다. 공개 소스 식별은 배포 SHA와 manifest/변경 파일 hash 등 확인 가능한 근거로 연결한다. 단지 배포 작업 성공을 실제 화면 통과로 간주하지 않는다.
- 결함이 남으면 영향 구간을 수정하고 재검증한다. 재현되는 배포 회귀는 [발행·복구 기준](RELEASE_OPERATION_GUARD.md)에 따라 다룬다. 후보/반려 기록은 최종 증거와 구별해 보존한다.
- 문서만 바꾸는 이 SOP 수립에는 게임 빌드/브라우저 테스트를 하지 않는다. 문구·링크·원격 반영을 확인한다.

## 9. 장별 기록 양식

```text
막/장/내부 ID:
기준 master / 공개 배포 및 식별 근거:
외곽·접합 목록: 위치 ID, 자산 ID, 월드 구간, 의도된 빈 공간/부유체 근거
검사 행렬: 위치 ID × 전체/보행/확대/극단 pan/모바일/상태
각 증거: 날짜, renderer, CSS W×H, DPR, camera x/y/zoom 또는 UI 재현,
         상태, 캡처 경로, 실제 공개/로컬 브라우저/Native/실기기 구별
발견: 위치, 절단/틈/합성/등록/미술/기능, 재현, 영향, 원인
수정: 파일·보존 범위, 시안/추적 필요 여부와 이유
측정: raw/후보 수치, 단위·기준 출처, ROI, 실패 표본, 관련 데이터 비교
검증: 실행 명령/결과, 실제 입력과 결과, 저장 분리/복원, 미실행 범위
원격/배포: commit, CI, Pages, 공개판 동일성
판정: 확인한 범위의 결함 유무 / 남은 결함 / 미검수 / 해당 없음(근거)
다음 행동:
```

검사 셀은 `미검수 / 결함 확인 / 수정 후 로컬 확인 / 배포 후 확인 대기 / 확인 범위 통과 / 차단 / 해당 없음(근거)`으로 구별한다. 기존 증거를 재사용하면 동일한 자산·합성·카메라·상태임을 확인하고 출처를 연결한다. 해당 없는 셀을 검사 성공 수에 넣지 않는다.

전 장 현황은 장마다 위 기록을 연결하고 필수 미검수 수·미해결 결함 수를 그대로 집계한다. 이 항목의 완료는 모든 장의 해당 목록과 상태를 확인하고 차단 결함/필수 미검수를 해소했을 때만 선언한다. 사용자 미감 승인, 모든 기기 보증, 전체 게임플레이 정량 검수의 완료와는 끝까지 분리한다.
